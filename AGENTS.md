# Case G agent guide

## Purpose

This project supports Mr. Gibbs, Associate Head of School at Pomfret School, with the school's seated meals: formal dinners where every student and the attending faculty sit at assigned round tables and some students wait on their table. He builds every list by hand today. The tool, in Google Sheets, seats the faculty (with households and guests), seats the students by rules he picks and ranks, picks waiters fairly across the year, checks every rule and writes the tabs he shares. He reviews and edits the result; the tool never has the last word.

## Safety rules (they don't bend)

- The repo is public. Build and test with made-up people only. Never put a real student's or faculty member's name, email, table or any other detail in code, tests, fixtures, docs, commit messages or PR text. Club members' names as the team are fine. Practice emails end in @example.org.
- Nobody working on the code sees the real data or asks for it. The real run happens in Google Sheets, in the school's Google account, by a person.
- No AI, no model calls, no network, no new dependencies. Plain JavaScript in Apps Script; plain Node for tests and scripts.
- The program never writes to the tabs people fill in (Students, Faculty, Faculty list, Past event). Only Make practice data writes those, and only into a spreadsheet whose Students and Faculty tabs are empty.
- The shared tabs (SM By first name, SM By form, SM By table, SM Faculty) show only names, form, table, role and guests.
- No sheet links, spreadsheet IDs or school email addresses anywhere in the repo.
- Add `.env.example` as soon as a credential or ID is needed (none is today). Never commit API keys, tokens or `.env` files. If a developer pastes a real credential into a file, stop and tell them.
- Don't merge, don't push to main, and don't edit `.github/CODEOWNERS`.

## Code layout

- `core/`: shared logic with no Sheets calls (reading, seating, history, outputs, practice data).
- `apps-script/Main.gs`: the menu, the handlers and the only code that touches SpreadsheetApp. Every write goes through its write helpers.
- `paste-into-apps-script/SeatedMeals.gs`: generated by `npm run bundle`; never edit it by hand.
- `tests/`: `npm test` (node:test) against a fake spreadsheet. `npm run demo` runs the whole flow on practice data.

## Working with student developers

- Prefer clear code over clever code. If you generate code the developer cannot explain, say so and explain what it does in plain English.
- Paths in this guide are relative to this standalone repository. Each club project has its own repo. Do not edit the archived `Civic-AI-Github-Repository` monorepo.
- For Git, branches, pull requests or merge conflicts, use the Developer Onboarding Guide linked below instead of making up a workflow.
- Check with Cayden before changing `.github/` or `.cursor/rules/`. Keep the README accurate when setup changes.

## Git and pull requests

- Never push directly to `main`. Work on a branch and open a pull request. Merging needs at least one approving review.
- Name branches `feature/<short-description>`, `fix/<short-description>` or `chore/<short-description>`, using lowercase letters and hyphens, with no spaces.
- Make small, frequent commits with plain-English messages.
- Use `.github/pull_request_template.md` for pull requests.
- Never add `Co-authored-by`, `Generated with`, `Made-with`, `Claude-Session` or any other AI attribution line to a commit message or pull request description. When squash merging, delete any such lines GitHub adds to the merge message.

## Beginner quick start

Full guide: https://github.com/CivicAIClub/docs/blob/main/developer-onboarding.md

1. First time: check Git with `git --version`, set your Git name and GitHub email, accept the club invite, and sign in with GitHub Desktop or `gh auth login`. Clone only your project's repo, open its folder, and read its README setup steps.
2. Start each work session from the latest main, then make a branch:

```sh
git checkout main
git pull origin main
git checkout -b feature/short-description
# Make and check your changes before continuing.
git status
git add .
git commit -m "Describe your change"
git push --set-upstream origin feature/short-description
```

Use `feature/`, `fix/`, or `chore/` as appropriate, with lowercase names and hyphens. Commit small working pieces; do not edit or push main directly.
3. Open a PR on GitHub, fill in the template, and get someone else's approval and passing checks where CI exists. Push review fixes to the same branch. After it is merged, pull main again before starting another branch.
4. If stuck, ask in the case chat, then Keke, then Luke or Cayden. Ask before doing anything drastic.
